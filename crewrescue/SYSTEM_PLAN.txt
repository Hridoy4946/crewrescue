1. SYSTEM OVERVIEW & ARCHITECTURAL OBJECTIVES
--------------------------------------------------------------------------------
CrewRescue is an emergency-resilient field operations and workforce dispatch 
platform engineered for critical infrastructure utilities.

Standard enterprise field management platforms operate under steady-state 
assumptions, resulting in high reassignment churn and delayed response times 
when severe weather, grid substation trips, or mass outages occur. CrewRescue 
addresses this operational failure mode through:
  1. Automated incident triage with deterministic fallback classification
  2. Multi-objective heuristic schedule optimization with state locking
  3. Human-in-the-loop dispatch approval with explainability metrics
  4. Real-time WebSocket synchronization across web consoles and offline PWAs

--------------------------------------------------------------------------------
2. USER ACTORS & ROLE-BASED ACCESS CONTROL (RBAC)
--------------------------------------------------------------------------------
The system defines 11 operational and administrative roles:

A. Operational & Administrative Actors:
  1. EMERGENCY_MANAGER   : Declares and manages disaster levels (L0-L4), adjusts 
                           global priority weights, initiates regional overhauls.
  2. DISPATCHER          : Reviews triaged incidents, executes heuristic solvers, 
                           inspects explainability deltas, and commits schedules.
  3. FIELD_SUPERVISOR    : Monitors active field units, monitors crew telemetry, 
                           and oversees regional skill and asset distribution.
  4. TECHNICIAN          : Operates mobile client/PWA, executes task transitions 
                           (ACCEPTED -> EN_ROUTE -> ARRIVED -> IN_PROGRESS -> RESOLVED), 
                           and records consumed inventory and completion notes.
  5. OPERATIONS_DIRECTOR : Manages multi-tenant configurations, depots, fleet units, 
                           user privileges, and global SLA thresholds.
  6. AUDITOR / EXECUTIVE : Conducts retrospective analysis of optimization runs, 
                           SLA breach penalties, financial exposure, and audit logs.

B. Automated / System Subsystems:
  1. AI Triage Worker    : Parses raw incident descriptions, categorizes severity, 
                           and maps required certifications and parts.
  2. Optimization Solver : Computes multi-objective cost functions across unassigned 
                           tickets and available crew capacities.
  3. Emergency Monitor   : Evaluates incident arrival rates against SLA thresholds; 
                           dispatches alerts across active WebSocket channels.
  4. Real-Time Gateway   : Socket.IO WebSocket cluster synchronizing client states.

4. MATHEMATICAL FORMULATION (OPTIMIZATION COST FUNCTION)
--------------------------------------------------------------------------------
The scheduling solver minimizes the composite multi-objective cost function:

  Min Z = w1 * C_travel + w2 * C_sla + w3 * C_overtime + 
          w4 * C_criticality + w5 * C_unassigned + w6 * C_detour

Component Definitions & Calibrated Weights:
  • w1 (0.20): C_travel      = Total transit travel time and fuel consumption
  • w2 (0.35): C_sla         = Financial penalty per minute of SLA deadline breach
  • w3 (0.10): C_overtime    = Overtime labor cost beyond scheduled shift hours
  • w4 (0.15): C_criticality = High-priority infrastructure weighting multiplier
  • w5 (0.15): C_unassigned  = Penalty for unresolved / unassigned incident tickets
  • w6 (0.05): C_detour      = Secondary travel time to regional depots for parts

Hard Operational Constraints:
  1. Skill Eligibility: Skills(WorkOrder_i) ⊆ Skills(Technician_j)
  2. Immutability: Status IN ('EN_ROUTE', 'ARRIVED', 'IN_PROGRESS') is non-reassignable
  3. Shift Limits: Scheduled work time <= Shift Duration + Allowable Overtime
  4. Singularity: Each work order is assigned to at most one technician

5. MONOREPO STRUCTURE & CONTAINER TOPOLOGY
--------------------------------------------------------------------------------

Repository Monorepo Layout:
crewrescue/
├── apps/
│   ├── web/                           # Dispatcher Console SPA (React / Vite)
│   └── pwa/                           # Field Technician PWA (React / Workbox)
├── services/
│   └── api/                           # Core REST & WebSocket Gateway (Express / Node.js)
│       ├── src/models/                # Mongoose domain models
│       ├── src/routes/                # API route controllers
│       ├── src/socket/                # Socket.IO connection handlers
│       └── scripts/seed.js            # Deterministic dataset generator
├── packages/
│   └── shared/                        # Shared contracts, enums, DTOs
├── infrastructure/
│   ├── docker/                        # Multi-stage Dockerfiles & Nginx configs
│   └── compose/                       # Compose orchestration manifests
└── docker-compose.yml                 # Root container orchestrator

Containerized Services:
  • Service 1: crewrescue-web    (Port 5173 / 80) -> Nginx serving Vite SPA
  • Service 2: crewrescue-api    (Port 5000)      -> Node.js API / WebSocket gateway
  • Service 3: crewrescue-mongo  (Port 27017)     -> MongoDB with volume persistence
  • Service 4: crewrescue-redis  (Port 6379)      -> In-memory queue and telemetry cache
